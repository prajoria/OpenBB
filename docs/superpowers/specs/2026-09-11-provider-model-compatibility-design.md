# Provider Model Compatibility Design

**Issue:** #2079  
**Status:** Approved for autonomous execution by the issue request

## Problem

`ProviderInterface` creates Pydantic response models named
`OBBject_<StandardModel>` and assigns their `__module__` to
`openbb_core.app.provider_interface`. Generated or previously built OpenBB modules
can therefore emit normal Python imports such as:

```python
from openbb_core.app.provider_interface import OBBject_EtfCountries
```

The named class is not bound in that module, so the import contract advertised by
the class metadata is false. An affected ETF module fails while the TechTrade
segment universe is resolving. TechTrade then intentionally falls back to its
unfiltered candidate path; if that path yields no candidates, live segment signals
are empty.

## Constraints and Success Criteria

- Fix the provider-model contract in `openbb_core`, not through a TechTrade
  monkeypatch or a special case for `EtfCountries`.
- Every dynamically generated response annotation must be importable from the
  module and name declared by the class.
- Keep lazy provider discovery and existing `ProviderInterface` semantics.
- Preserve TechTrade's logged fallback from a failed universe lookup to no filter.
- Do not broaden exception handling or hide provider failures.
- Add a regression test that fails on the current implementation and covers
  `OBBject_EtfCountries` plus the generic model contract.
- Run focused core/provider and TechTrade tests, then the opt-in live signal test
  when the configured environment permits it.

## Considered Approaches

### 1. Register generated models in their declaring module (recommended)

Create each response annotation with an explicit
`__module__="openbb_core.app.provider_interface"` and bind it in that module's
globals when `ProviderInterface` builds its annotation map.

This makes ordinary Python import semantics match the model metadata for every
provider model. It is generic, small, and keeps existing generated packages
compatible.

### 2. Filter `OBBject_*` imports from generated packages

Teach `ImportDefinition` never to emit response-model imports. This improves future
generated output but does not repair already generated or independently installed
consumers that rely on the advertised module/name pair. It also preserves the
underlying false metadata contract.

### 3. Add module-level dynamic `__getattr__`

Resolve missing `OBBject_*` names on demand by constructing a
`ProviderInterface`. This supports stale imports, but introduces implicit work and
recursive-import risk in a magic attribute hook. It is harder to reason about than
registering models when they are created.

## Design

Update `_generate_return_annotations` so each created Pydantic model:

1. receives the provider-interface module explicitly through `create_model`;
2. is stored in the returned annotation map as before; and
3. is exported under its generated class name in the same module.

No provider-specific branches are added. Repeated interface construction may
replace an export with the newly generated equivalent class, matching the existing
annotation-map replacement semantics.

## Data and Error Flow

Provider registries still feed `_generate_return_annotations`; query execution,
provider selection, and result validation are unchanged. The only added operation
is binding a successfully created class. Model-construction failures continue to
propagate.

TechTrade's segment path remains unchanged:

1. resolve ETF holdings;
2. on a resolver failure, log and widen to the existing no-filter fallback;
3. rank candidates, which may legitimately be empty.

The compatibility fix prevents the false `ImportError` before this fallback is
needed, without changing fallback behavior for genuine network, credential, or data
failures.

## Testing

- Add a core regression asserting every generated response model can be resolved
  from `model.__module__` by `model.__name__`, with an explicit
  `OBBject_EtfCountries` assertion when that model is installed.
- Keep and run the TechTrade fallback test proving resolver failures still return
  `None` (no filter) and emit the expected warning.
- Run focused provider-interface/package-builder tests and TechTrade
  universe/movers/signals suites.
- Drive a fresh-process import of `OBBject_EtfCountries` after
  `ProviderInterface` initialization and capture the output.
- Run the opt-in live signal integration test; a credentials/network skip is
  acceptable, but a provider-model `ImportError` is not.

## Non-Goals

- Changing TechTrade's fallback policy.
- Special-casing ETF countries or modifying provider packages.
- Regenerating or committing the autogenerated `openbb.package` tree.
- Treating empty live market data as a provider compatibility error.
