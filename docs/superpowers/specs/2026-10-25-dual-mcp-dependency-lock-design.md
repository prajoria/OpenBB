# Dual-MCP dependency lock — design

- **Issue:** #2245 ([mcp-parity] Lock complete dual-MCP transitive dependency graphs)
- **Parent:** #2135 (F2.1), deferred from #2159 review
- **Branch:** `feat/dual-mcp-lock-gh-2245` → PR into `portfolio`
- **Status:** design approved by "design it and go" (questions waived); technical calls below are the author's.

## 1. Intent

`scripts/start-dual-mcp.ps1` builds two ephemeral environments with
`uv run --no-project`:

| Environment | Direct requirements today | Transitive graph today |
|---|---|---|
| Platform MCP (`isolated_uv` installation, `platform-standard` profile) | `fastmcp==3.4.0` + 4 checkout-local editables (`openbb_platform`, `core`, `extensions/platform_api`, `extensions/mcp_server`) | re-resolved from upstream ranges on every fresh env (~146 packages) |
| Workspace MCP | `fastmcp==3.4.6`, `openbb-ai==2.1.0`, `pydantic==2.12.5`, `starlette==1.6.0`, `uvicorn==0.52.3`; app module run from the Workspace checkout via `--directory` | re-resolved on every fresh env (~72 packages) |

Direct pins are exact, but every transitive dependency floats. A new upstream
release of any of ~200 packages can silently change what the launcher runs.
The `third_party/workspace/backend-api/backend/uv.lock` does not help:
`--no-project` deliberately ignores it.

The goal: the launcher runs a **known, reviewed, complete dependency graph**
for both servers, and any change to that graph is an explicit, diffable commit.

The `portfolio_venv` installation (portfolio profiles) is out of scope. It runs
a pre-built `.venv_portfolio` interpreter and does no launch-time resolution.

## 2. Goals / non-goals / anti-goals

**Goals** (the #2245 acceptance criteria):

1. A committed, owned lock artifact for **each** environment covering the full transitive closure.
2. The launcher consumes it and cannot resolve newer transitive versions.
3. A refresh workflow (deliberate upgrade), a check workflow (drift gate), and a clean-env replay test.
4. #2159 checkout-local editable-source validation preserved unchanged: the 4 Platform editables still come from the checkout via `--with-editable`, and the Workspace app still comes from the Workspace checkout via `--directory`.
5. The Platform FastMCP 3.4.0 / Workspace FastMCP 3.4.6 split documented as intentional.

**Non-goals:** changing the portfolio-venv install path; locking the Workspace
backend's own Poetry/uv project; Linux/macOS launcher support (the launcher stays
Windows-only, though the locks are universal); auto-merging upgrades.

**Anti-goals** (would be a failure even if it "works"):

- A lock that *looks* applied but isn't. Verified trap: `uv run` silently
  **ignores `UV_CONSTRAINT`**. A spike with constraint `idna==3.6` installed 3.20.
  Constraints-file designs are therefore rejected.
- Lock files leaking operator-local absolute paths (PII rule) or churning per machine.
- Hand-maintained pin lists duplicated across launcher, test, and lock.

## 3. Approach (decided)

### Options considered

| Option | Verdict |
|---|---|
| A. Convert each env into a throwaway uv project (`pyproject.toml` + `uv.lock`, `uv run --frozen`) | Strongest uv-native guarantee, but editables become path deps in a synthetic project, which changes the #2159 `--with-editable` provenance semantics and adds two fake projects. Rejected. |
| B. Constraints file (`UV_CONSTRAINT`) | `uv run` 0.11.26 has no `--constraints` flag and ignores the env var (proven above). Rejected. |
| **C. Fully pinned requirements lock per env, consumed via `uv run --with-requirements`, compiled by `uv pip compile --universal`** | **Chosen.** Spike-verified for both envs: Platform 146 pins, Workspace 72 pins, zero local paths, compile ~2 s, launch OK. Editables coexist with the pins. A conflicting pin is a hard resolver error (fails closed). |

### Artifacts

```
scripts/mcp_locks/
  platform-mcp.in     # direct inputs: fastmcp==3.4.0 + 4 relative "-e ../../openbb_platform/..." lines
  platform-mcp.txt    # generated: universal, editables excluded via --no-emit-package (no hashes, see section 7)
  workspace-mcp.in    # direct inputs: the 5 Workspace pins
  workspace-mcp.txt   # generated
scripts/lock_mcp_envs.py   # generator / checker
```

- `.in` files are the **single source of truth** for direct pins. The inline
  `--with pkg==ver` arguments are removed from the launcher. The FastMCP-split
  rationale moves into a comment at the top of each `.in` file.
- Compilation runs with `cwd = scripts/mcp_locks` and relative paths, so `# via`
  annotations stay machine-independent. Output uses `--no-header`. The generator
  writes its own header:

  ```
  # Generated by scripts/lock_mcp_envs.py from platform-mcp.in — do not edit.
  # Refresh: python scripts/lock_mcp_envs.py --upgrade
  # locked-at: 2026-10-25T05:00:00Z
  ```
- Locks are `--universal --python-version 3.13`, so one file serves the Windows
  launcher and Linux CI. Packages not needed on the current platform are skipped
  via environment markers.

### Launcher consumption

- Platform: `uv run --no-project --python 3.13 --exclude-newer <locked-at> --with-requirements scripts\mcp_locks\platform-mcp.txt --with-editable <same 4 paths>`.
- Workspace: `uv run --no-project --python 3.13 --exclude-newer <locked-at> --with-requirements scripts\mcp_locks\workspace-mcp.txt --directory <WorkspaceBackend> python -m workspace_mcp ...`.
- **`--exclude-newer <locked-at>`** closes the remaining gap. If an editable's
  `pyproject.toml` gains a dependency that is not yet in the lock, that package
  cannot resolve to anything newer than the lock date. It is never "latest". The
  CI check (below) then fails the PR until the lock is regenerated.
- The launcher throws if a lock file is missing or lacks a parseable `locked-at` line.
- Argument construction moves into two exported functions in
  `scripts/mcp_stack_lifecycle.psm1`: `Get-PlatformUvArguments` and
  `Get-WorkspaceUvArguments`. The launcher and the replay test share one
  definition, so the test replays exactly what ships.

### Generator modes (`scripts/lock_mcp_envs.py`)

| Mode | Behavior |
|---|---|
| default (sync) | Recompile, **preserving existing pins** (uv keeps versions already in the output file). Adds/removes only what changed inputs require. Bumps `locked-at` only when content changes. |
| `--upgrade` | Recompile with `--upgrade`: the deliberate refresh. The result lands through a normal reviewed PR. |
| `--check` | Sync-compile into a temp copy and diff against the committed lock, ignoring `locked-at`. Also cross-checks that `runtime_profiles.json` `required_versions.fastmcp` equals the Platform lock's `fastmcp` pin. Exit 1 on any drift, with a unified diff. Never writes. |

### Verification

1. **Pester** (`scripts/tests/Start-DualMcp.Tests.ps1`, updated):
   - The launcher passes `--with-requirements` + `--exclude-newer` for both envs and no inline `pkg==ver` `--with` pins.
   - The 4 `--with-editable` paths equal the `-e` lines in `platform-mcp.in` (guards #2159).
   - Pins move from the script-text regexes to the `.in` files (`fastmcp==3.4.0` / `3.4.6` split asserted there).
   - The missing-lock and missing-`locked-at` failure paths throw.
2. **pytest** for `lock_mcp_envs.py`: header/locked-at parse, `--check` detects an injected drift and passes on a clean tree, and the required_versions cross-check fails on mismatch. Each load-bearing test is reverse-verified per CLAUDE.md testing rule 7.
3. **Clean-env replay** (`scripts/test_mcp_lock_replay.ps1`): with an empty temporary `UV_CACHE_DIR`, run each env using the shared argument functions and execute `scripts/mcp_locks/assert_lock_replay.py <lock>` inside it. That script asserts every installed non-editable distribution appears in the lock at the exact version, and every lock entry whose marker applies is installed.
4. **CI workflow** `.github/workflows/dual-mcp-lock.yml`:
   - `lock-check` (ubuntu): `python scripts/lock_mcp_envs.py --check` on PRs touching locks, `.in`, editable `pyproject.toml`s, the launcher, or the lifecycle module.
   - `replay` (windows-latest, submodule checkout): Pester suite + clean-env replay.
   - `refresh-report` (weekly `schedule` + `workflow_dispatch`): run `--upgrade` into the workspace and publish the diff as a job summary + artifact. It **does not push or open PRs**. Upgrades land via a human-driven dev cycle.

### Documentation

`docs/operations/portfolio-mcp.md` gains a "Dependency locks" section: what is
locked, refresh/check commands, why `UV_CONSTRAINT` is not used, and the FastMCP
split. FastMCP 3.4.6 requires Starlette ≥ 1.0.1, which conflicts with the
Platform's FastAPI. The Platform therefore stays on 3.4.0 / Starlette 0.52.x,
while the Workspace server runs 3.4.6 / Starlette 1.6.0 in its own env. The two
never share an interpreter.

## 4. Constraints

- uv ≥ 0.11 (current 0.11.26) for `--with-requirements`, `--exclude-newer`, `--universal`.
- Python 3.13 for both envs (unchanged).
- No absolute or operator paths in committed artifacts (enforced by a pytest that scans the lock files).
- CI General Linting: the new Python files pass black (88 cols), ruff, mypy, and pylint.

## 5. Settled during builder check (author's calls, spike-verified)

- **`locked-at` is the exact UTC compile timestamp, never a date.** A spike with
  a midnight cutoff failed closed: `cachetools 7.2.5` was published at 08:53Z the
  same day. A date-granular stamp would break fresh launches.
- Relative `-e ../../…` inputs compiled from `scripts/mcp_locks` produce zero path
  leakage, and sync mode preserves existing pins (verified by hand-pinning `idna`).
- `assert_lock_replay.py` uses `packaging.markers` from inside the replayed env
  (`packaging` is pinned in both locks).
- No CI job runs Pester today. The new workflow installs **Pester 4.10.1**
  explicitly; local machines ship 3.4.0. The suite keeps v3/v4-compatible
  `Should Be` syntax, which Pester 5 would reject.
- One issue → one PR. #2245 is the single deliverable, so no extra sub-issues
  are filed for plan steps.

## 7. Amended during final review

- **Hashes dropped.** The original design compiled with `--generate-hashes`. Final
  review proved `uv run --with-requirements` never verifies them: a lock with a
  corrupted `idna` hash installed cleanly on an empty cache, and `UV_REQUIRE_HASHES`
  and `UV_VERIFY_HASHES` are both ignored by `uv run`. Unverified hashes would be
  this design's own anti-goal (a lock that looks applied but isn't). The locks
  therefore pin exact versions only, which is what #2245 requires and what `uv run`
  enforces. Launch-time artifact integrity needs a different launcher model (a
  persistent environment built with `uv pip sync --require-hashes`) and is tracked
  as a follow-up issue.
- **Interpreter-bundled packages.** The clean-cache replay found `pip` installed in
  the uv-managed base interpreter, outside the environment. The replay asserter
  judges only distributions installed into the environment.
