# T5 Paper/Live Broker Adapter Design

**Issue:** #1719  
**Status:** Approved by the autonomous execution request on 2026-09-11

## Gap analysis

The existing T5 stack is a partial execution path:

- `OrderSink` is an artifact-export contract. `PaperOrderSink` writes CSV/XLSX but
  deliberately performs no broker submission.
- `/tt/execute/write-batch` has auth, environment, verdict, and `confirm=yes`
  gates, but always submits a fixed demo batch directly to
  `SqlitePaperEngine`.
- `PaperEngine` persists pending orders and lifecycle changes, but repeated
  `submit_batch` calls create duplicates and its IDs contain only a truncated
  UUID tail.
- There is no paper/live adapter contract, durable cross-backend submission
  journal, live-mode kill switch, client-order idempotency contract, or
  recoverable partial-submission semantics.
- `MysqlPaperEngine` now has the corrected #2059 pool contract
  (`with pool.get_connection()`, explicit transaction, commit before return,
  rollback on all failures). The new paper adapter must use
  `get_default_engine()` rather than bypassing it with a hard-coded SQLite
  engine.

## Considered approaches

1. **Add live methods to `OrderSink`.** Rejected: artifact export and
   irreversible broker side effects have different lifecycle and safety
   contracts.
2. **Put paper/live branching in the widget endpoint.** Rejected: it makes HTTP
   code own idempotency, audit persistence, and cancellation semantics, and is
   not reusable from notebooks or CLI callers.
3. **Introduce a broker adapter plus execution gateway and durable journal.**
   Chosen: adapters translate backend calls; one gateway owns confirmation,
   gates, idempotency, audit, and error semantics.

## Architecture

`ExecutionGateway` accepts a validated `OrderBatch` and delegates to a
`BrokerAdapter` selected explicitly as `paper` or `live`.

- `PaperBrokerAdapter` wraps the public `PaperEngine` protocol. Its default
  factory calls `get_default_engine()`, thereby using the corrected pooled
  MySQL implementation when configured.
- `LiveBrokerAdapter` wraps an injected `LiveBrokerClient` protocol. It imports
  no vendor SDK, reads no credentials, and cannot make a network call unless an
  application explicitly injects a client. The client must expose its
  broker-verified provider and account identities, which must match the
  configured scope before every submit/cancel. Client order UUIDs are passed
  to the client as idempotency keys.
- `SqliteExecutionAuditStore` is a local durable journal with submission,
  per-order, and append-only event rows. A unique `(mode, account,
  batch_sha256)` key prevents a second execution of the same batch.

The live client boundary is intentionally vendor-neutral. Alpaca, IBKR, or a
safe fake can implement the same methods without changing the gateway.
`POST /tt/execute/approve-plan` is the production handoff: it runs T4
validation server-side (or a server-injected equivalent), registers only a
robust immutable batch, and returns its approval ID and confirmation phrase.

## Safety and confirmation

All submissions require:

1. authenticated caller at the HTTP boundary;
2. T4 verdict `PASS` and `OrderBatch.verdict_gate_pass=True`; live mode must
   resolve that immutable batch from the server-owned approved-plan registry,
   never construct it from caller-controlled verdict input;
3. `PI_ALLOW_T5_EXECUTE=true`;
4. an exact, batch-bound confirmation phrase generated by the gateway.

Live mode additionally requires:

1. `PI_T5_BROKER_MODE=live`;
2. `PI_ALLOW_T5_LIVE=true`;
3. a non-empty configured account identifier matching the adapter;
4. confirmation containing `LIVE`, the account identifier, and the batch SHA.

Paper remains the default. There is no fallback from live to paper: a missing
client, gate, account, or confirmation fails closed.

Cancellation is separately confirmed with an exact phrase bound to the order
UUID. Repeated cancellation returns the existing terminal result. Filled or
otherwise terminal orders are rejected by the underlying adapter.

## IDs, idempotency, and audit

Each submission and submitted order receives a full RFC 4122 UUID. Order UUIDs
are derived deterministically from the submission UUID and ordinal so retries
use the same client-order IDs.

The audit store reserves the `(mode, broker_id, account_id, batch_sha256)`
idempotency key before any broker side effect.
Terminal retries return the stored receipt without invoking the adapter.
Retries against an in-progress/unknown-outcome submission fail closed for
operator reconciliation rather than risking a duplicate.

Every transition appends an audit event. Adapter acknowledgements preserve both
the internal order UUID and the backend's broker order ID.

## Error semantics

- Gate and confirmation failures raise typed errors before audit reservation or
  broker calls.
- A definite backend rejection before any acknowledgement records `FAILED`; a
  definite rejection after acknowledgements records `PARTIAL`.
- A transport exception can mean the live broker accepted an order but its
  response was lost. It records `RECONCILIATION_REQUIRED`/`UNKNOWN`, preserves
  known acknowledgements, and fails closed without automatic retry.
- Cancellation is atomically reserved as `CANCELLING` before the broker call.
  Concurrent requests fail closed, and an ambiguous backend failure records
  `CANCEL_RECONCILIATION_REQUIRED` instead of retrying.
- No exception triggers fallback to another execution mode.

## Verification

Tests use only SQLite temporary files, fake paper engines, and an injected fake
live client. They cover gates, exact confirmation, deterministic UUIDs,
idempotent retries, durable audit replay, partial failures, cancellation, live
fail-closed behavior, adapter protocol conformance, and the #2059 default paper
factory path. A Phase-6 harness will drive paper and fake-live flows end to end;
it must never use brokerage credentials or contact a brokerage.
